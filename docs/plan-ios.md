# iOS plan — fully on-device Reference Frame for iPhone

Status: **planning** (started 2026-10-01). Version number TBD — the 0.5.0
slot is still video playback on desktop; this is likely its own major line.

Goal: a standalone iPhone app — record at practice (or import), analyze
entirely on the phone, review report cards / gap bars / Compare, run
Insights — usable with no desktop at all (e.g. at a convention).

## Decisions locked 2026-10-01

- **Fully on-device.** No server, no desktop dependency.
- **Separate worlds.** iOS runs gap-compare only against pros that were
  also analyzed on iOS. Desktop pro baselines are not imported. The
  "both sides through the same metrics code path" invariant holds *within*
  each platform. Desktop stays byte-identical to the vendored source;
  nothing in this plan touches `engine/`.
- **SwiftUI native UI**; pipeline in native Swift (Accelerate / CoreML /
  Vision / AVFoundation).
- **No Apple Developer account yet.** Free provisioning: dev-device
  installs, 7-day re-sign, no TestFlight/App Store. Revisit before any
  distribution (see §Distribution).

## What the engine actually does (audit 2026-10-01)

| Stage | Desktop today | iOS replacement (proposed) |
|---|---|---|
| Decode | OpenCV, two full decodes | AVAssetReader, single pass feeding both detection and refine |
| Detect + pass-1 pose | ultralytics `yolov8m-pose` (AGPL — cannot ship) | Apache/MIT detector in CoreML (RTMDet / YOLOX) or `VNDetectHumanRectanglesRequest(upperBodyOnly:false)` — spike decides |
| Tracking / identity | custom: frozen torso HSV-histogram anchors + spatial cost, greedy, 2 dancers (`pose_extraction.py:60-330`); seeded crowd mode | straight Swift port (vImage histograms, Bhattacharyya) — no Vision equivalent |
| Refine (2D) | rtmlib RTMPose-m Halpe-26 ONNX, top-down from pass-1 boxes | RTMPose-m → CoreML. **Must keep Halpe-26** — Apple's 19-joint body pose has no heels/toes, which kills ball-foot %, toe-first, rise/fall |
| 3D lift | VideoPose3D TemporalModel, 243-frame, per dancer independently | same net on device (MPSGraph or CoreML). Apple's 3D request rejected: per-frame, single-person, different skeleton, no temporal smoothing |
| Audio | ffmpeg → 22050 mono → librosa `onset_strength`, tempo-prior autocorr, `beat_track(bpm=…)` DP, `rms`, `hpss` | AVAudioFile + resample, Swift/vDSP ports of each |
| Metrics | `dance_metrics.py` 2720 lines, ~57 registered metrics; scipy `savgol_filter`, `butter`/`filtfilt`, `find_peaks`, `hilbert`, `correlate`, `pearsonr`; numpy fft/interp/polyfit/2×2 eig | Swift port in a `RefFrameKit` package; DSP primitives ported to match scipy edge semantics |
| Report/gap | `dance_review.py` text + `run.py:_gap_report` | Swift; keep `metrics.json` keys identical so the registry carries over |

No stage needs two dancers' 3D simultaneously — all pair metrics are 2D.

## Licensing (load-bearing, same spirit as desktop)

- **No ultralytics code or YOLO weights** in the iOS binary or downloads.
- **VideoPose3D (CC-BY-NC):** download-on-first-run from upstream ONLY.
  We may not host a converted `.mlpackage` — that's redistribution through
  a channel we control. So the phone must load the upstream `.bin`
  (torch zip/pickle checkpoint) and build the net itself (MPSGraph, or
  assemble a CoreML spec on-device + `MLModel.compileModel`). **Spike #1.**
- **RTMPose / detector (Apache/MIT):** redistribution is legal. Open
  question: keep the desktop's uniform "everything downloads on first run"
  policy by hosting our converted CoreML files as release assets, or
  bundle them? Recommend: first-run download from our release assets —
  keeps the install small and the policy uniform.
- **App Store vs AGPL:** iOS code is new, written by the maintainer, and
  contains no third-party AGPL code, so it can carry an App Store
  exception (or a different license). Confirm sole authorship of anything
  reused from desktop (registry, explainers, `prompts/coach-system.md`).
  Only matters once distribution is on the table.

## Validation strategy (replaces golden diffs for iOS)

"Separate worlds" removes the cross-platform comparability requirement,
not the correctness requirement. Stage-wise, run on a Mac via `swift test`:

1. **DSP primitives** — each scipy/numpy/librosa function vs fixtures
   generated by a Python script from `engine/.venv`; tight tolerances
   (`filtfilt`, `savgol` edge modes, `find_peaks` prominence/distance,
   `onset_strength`, `beat_track` DP, `hpss`).
2. **Metrics given poses** — feed a desktop `<stem>_poses.json` +
   extracted audio into Swift metrics; compare to desktop
   `_metrics.json` per key with per-metric tolerances. (Analog of golden
   diff #2: same inputs both sides.)
3. **Pose stages** — per-stage keypoint error vs desktop on a small
   golden-video set (your own practice clips, kept out of git as always).
4. **End to end** — metrics distributions on the golden set should land
   near desktop; differences are documented, not required to be zero.

Fixture generator lives in `ios/tools/` and never changes `engine/`.

## Phases

**P0 — Spikes (go/no-go before committing):**
1. VideoPose3D from upstream `.bin` running on iPhone; output matches
   torch within float tolerance. → [spike-ios-1-videopose3d.md](spike-ios-1-videopose3d.md)
2. RTMPose-m Halpe-26 → CoreML: accuracy vs ONNX, ms/frame on device.
3. Detector choice: Vision human rectangles vs CoreML RTMDet/YOLOX —
   recall on partner-dance footage (occlusion, crowds).
4. Throughput + thermals: a 3-min 1080p clip end to end on a target
   iPhone. If it's too slow: frame stride for pose (affects metrics —
   desktop analyzes every frame) vs lower input res vs just accepting it.
5. Long-running work: verify iOS background-continuation options for a
   multi-minute user-initiated job (iOS 26 `BGContinuedProcessingTask`
   — confirm API and free-provisioning entitlement limits).

**P1 — `RefFrameKit` (Swift package, Mac-testable):** DSP primitives,
audio features, metrics port, report/gap, `poses.json`/`metrics.json`
codecs. Validation steps 1–2.

**P2 — Pose pipeline in Swift:** decode, detect, identity tracking (incl.
seeded crowd mode), refine, lift, orientation/role. Validation 3–4.

**P3 — SwiftUI app:** library; capture (camera) + import (Photos/Files);
seed-picking UI (tap the two dancers on a frame); analyze queue with
progress; report cards + gap bars + Compare; Pros tab (analyze a pro
video on-device → store metrics). Metric registry + explainers extracted
from `src/renderer/src/metrics/registry.ts` into a shared JSON both
platforms consume (small desktop refactor, no behavior change).

**P4 — Insights + notes:** direct Anthropic API with key in Keychain (no
CLI backend on iOS), same `prompts/coach-system.md` framing (observations
+ questions, never drills). Notes: export via share sheet / Files rather
than the desktop's vault writer (free provisioning has no iCloud
entitlement).

**P5 — Distribution decision:** Developer Program enrollment (also
unblocks mac signing/notarization backlog item), licensing exception,
TestFlight.

Not on iOS: yt-dlp URL sources (no Python; App Review risk) — local video
only.
